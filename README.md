# Delhivery Last-Mile Delay Intelligence Pipeline

## How to run

1. Clone or download this public GitHub repository.
2. Open a terminal in the project directory.
3. Install the required dependencies:

   ```bash
   pip install -r requirements.txt
   ```

4. The `data/`, `models/`, and `outputs/` folders contain the generated datasets, saved model artifacts, and analysis results.
5. Run the scripts from the project root as needed:

   ```bash
   python part_a_clean_eda.py
   python part_b_regression.py
   python part_c_classification.py
   python part_d_segments.py
   python package_model.py
   python predict_delay.py
   ```

   Run the stages in order because later stages may depend on files generated by earlier stages.

## Data findings

- The raw shipment dataset contained 1,224 rows.
- After removing duplicate records, 1,200 shipment records remained.
- The modelling table contains 1,200 rows and 26 columns.
- The median shipment distance is approximately 314.95 km.
- The median parcel weight is 1.83 kg.
- The median declared shipment value is approximately ₹1,121.50.
- Delivery-delay patterns were examined across service type, payment mode, hub, weather, and sale-event conditions.
- Hub segmentation grouped 24 hubs into Standard, Watch, and Escalate categories.

## Model results

### Regression

The selected regression model was Linear Regression.

| Metric | Test result |
|---|---:|
| Mean Absolute Error (MAE) | 3.5671 hours |
| Root Mean Squared Error (RMSE) | 4.5235 hours |
| R-squared (R²) | 0.9493 |

The test results indicate that the model explains a large proportion of the variation in delivery time on the evaluated dataset. These results should be validated on real operational data before deployment.

### Classification

The delay classifier was evaluated on a held-out test set.

| Metric | Test result |
|---|---:|
| Accuracy | 0.8667 |
| Precision | 0.6889 |
| Recall | 0.7561 |
| F1-score | 0.7209 |
| ROC-AUC | 0.9171 |
| Decision threshold | 0.50 |

The classifier identifies shipments at risk of delay. Precision and recall should both be considered when choosing an operational alert threshold.

## Operations recommendation

- Use predicted delay risk to prioritize shipments for review.
- Monitor hubs assigned to the Watch and Escalate segments.
- Consider proactive customer communication for high-risk shipments.
- Review weather, distance, service type, dispatch timing, and hub capacity when investigating delays.
- Treat model predictions as decision support, not as a substitute for operational judgement.

The generated prediction output contains 48 new shipments: 8 were predicted as delayed. The recommended actions include 6 escalations to hub managers and 2 proactive customer calls; 40 shipments were assigned no action.

## Production plan

1. Validate the pipeline on representative historical and live shipment data.
2. Schedule data-quality checks and monitor missing or unexpected values.
3. Integrate predictions with an operational dashboard or shipment-management workflow.
4. Track precision, recall, false alarms, and missed delays over time.
5. Retrain and recalibrate the model when shipment patterns change.
6. Keep human review and escalation procedures in place.

## Limitations

- The project uses generated shipment data, so the results may not represent real-world delivery performance.
- Evaluation metrics depend on the dataset, train/test split, and selected model settings.
- The classification threshold may need adjustment to reflect the cost of missed delays versus unnecessary alerts.
- Relationships found in the data do not establish causation.
- Real deployment requires validation, privacy and security checks, monitoring, and operational integration.
